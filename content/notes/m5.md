Core idea: a working build still has to survive reuse, review and deployment. Package it, contribute it, pin it, place it on a compliant platform, and hold every boundary.

## Packaging for reuse
- **Accelerator** = a solution packaged so the next engagement starts from a working base. Separate engagement-specific values from the reusable core; expose them as **parameters with documented defaults**. Package while the build is fresh.

| Asset | Parameterize | Document |
|---|---|---|
| **Agent template** | Prompts, paths, scopes, **credentials by reference**, thresholds | Env assumptions, inputs, failure modes, defining eval |
| **MCP server package** | Scopes, credentials by reference, per-customer paths | Inputs per tool, scope limits, failure modes |
| **Eval suite** | Thresholds, dataset paths | Rubric, score meaning, **pinned baseline** (also the deploy gate) |

- Ship eval **dataset and rubric together**.
- **Audit bundle** is part of the package: data touched, identity used, log left. Without it the asset stalls at security review.
- **Runs ≠ reusable.** Warning signs: no parameters, no assumptions doc, no bundled eval. Loose scripts are the common wrong approach.
- One-off never reused → skip packaging.

## Contributing back
| Channel | For |
|---|---|
| **Claude Cookbook** | Focused, self-contained reference pattern that runs end to end |
| The tool's **own repo** | An open-source MCP server, tool or fix |

- **Match channel first**: a full multi-component app in the Cookbook stalls.

**Readiness steps:**
1. **Rights and attribution check first**: customer licensing can block it. Can't clear it → don't contribute; escalate.
2. Code does **one thing**.
3. An **example** shows it running.
4. A **test** proves it works.
5. A short statement of **assumptions**.

- Maintainers accept what they can **verify**. An unverifiable PR waits even if the code works.

## Requirements & lifecycle
- **Functional requirement** = a checkable behaviour; it becomes an eval line. "Answer faster" is a problem, not a requirement.
- **Infrastructure requirements** (usually derived, not stated) decide the platform: **latency** (where the user is), **scale** (volume, peak), **residency** (where data is processed, which regulation), **identity** (who acts, what's auditable).
- "Data must not leave the EU" is **residency**, not functional. Capture these **before** a platform is picked for familiarity.
- **Requirements record** = behaviours + constraints + the regulation behind each.

**Lifecycle:**
1. Requirements
2. Design: platform, model, trust boundaries
3. Build: agent, tools, prompts
4. Test: evals, unit, integration, E2E
5. Deploy: **pin version, gate promotion on eval**
6. Operate: instrument cost, latency, errors; guardrails
7. Iterate: findings feed back into requirements

- **Gates** = where regulated projects keep control: no build until residency is met; no full rollout until the eval clears the baseline. Regulated deployments can't skip phases.

## Deployment & versioning
- **The customer's existing cloud usually picks the platform.** Identity and data location come from the platform, not your code.

| Platform | Key fact | Model IDs |
|---|---|---|
| **First-party API** | Anthropic identity; **new features first** | Full Claude ID |
| **Claude Platform on AWS** | Via AWS account; inference **outside** AWS boundary | Claude API format |
| **Claude in Amazon Bedrock** | Messages API; data **inside** AWS boundary | `anthropic.` prefix; partner retirement dates |
| Bedrock (legacy) | `InvokeModel`/`Converse` | ARN-versioned |
| **Vertex AI** | Google Cloud IAM, billing, regional/global endpoints | Vertex format |
| **Microsoft Foundry** | Hosted on Azure (some models) or on Anthropic | Platform controls |

- **Aliases move** (`opus` can change under you). **Pin the full model ID.** Older models pin with a date suffix (`claude-haiku-4-5-20251001`); 4.6+ IDs pin on their own.
- **Versioning**: pin the model, version prompts with code, **keep the prior version** for rollback.
- **Promote via eval**: canary a portion of traffic, compare to the pinned baseline, promote or roll back.
- Alias is fine for a throwaway prototype. "Pinning is for what ships."
- Partner retirement dates ≠ Anthropic's.

## Comparing platforms
| Measure | How | Usually wins |
|---|---|---|
| **Compliance** | Against existing certifications and residency, **at scoping** | Cloud the customer already certified |
| **Latency** | From the **customer's region with real payloads** | In-region cloud on round trip |
| **Cost** | **Total per call**: tokens + egress + platform fees + integration | Lowest total, not cheapest token |

- Order: hard compliance gate → latency → total cost. If compliance is pass-or-fail, it decides placement; skip the comparison.
- EU-only data → typically **Bedrock or Vertex AI**. First-party API may lack EU residency; Anthropic-hosted Foundry models don't meet EU residency. In Bedrock, global vs regional endpoint is the residency control.
- Token rates are broadly aligned; total cost moves on everything else. Laptop latency hides the round trip.
- **Easy to build ≠ allowed to ship.**

## Trust boundaries
- Multi-component app: API orchestrator → Claude Code task → MCP server → customer system. **Map who does what before connecting.**
- **Every seam is a trust boundary**, even between components that pass their own tests. Fetched content is **data, not authority**, downstream.
- **The app is only as contained as its most privileged seam.** Least privilege applies app-wide.

| Component | Seam risk | Control |
|---|---|---|
| First-party API (orchestrator) | Requests from outside | Input validation + call identity |
| Claude Code task | Fetched content | Treat as data at the next seam |
| MCP server | Holds customer-system access | Least-privilege scope + **access logs** |

- Confirm ZDR and HIPAA BAA eligibility **per component**.
- A seam you can't secure → don't ship around it; **escalate to a human owner**.
