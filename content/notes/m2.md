Core idea: make Claude integrations structurally reliable under tool calls, streams, long context and failures.

## Prompting craft
**Diagnose, don't reword.** The type of failure names the missing technique:

| Observed failure | Add |
|---|---|
| Wrong shape (prose instead of a label or JSON) | **Output constraint**: allowed values, field names, where to stop |
| Scope or tone drift, worse deeper into the chat | **System prompt** (or a more specific one) |
| Task right, structure invented | **Few-shot examples**: show, don't describe |
| Clean on tests, breaks on one variant | **A constraint or example for that variant** |

- Loop: name the failure → add the one matching technique → re-run → diagnose again. **Three failed rewrites in a row → stop adding text.**
- **System prompt** = persistent contract: role, output format, rules that must not change.
- **XML tags** (`<ticket>`, `<ideal_output>`) keep examples and data apart from instructions.
- Stack all four only for a strict output contract; a simple task stays simple.
- **Verbose prompt → verbose output**: longer prompts add latency, not accuracy.

**Structured outputs: a prompt is a request; these enforce the format** (constrained decoding):

| Mode | Set | Constrains |
|---|---|---|
| JSON outputs | `output_config.format` → type `json_schema` | **Final response** |
| Strict tool use | `strict: true` on the tool | **Tool arguments** |

- First call with a new schema is slower (compiled to a grammar, cached 24h); it also adds input tokens.
- **Can't be combined with prefilling.**
- Still check `stop_reason`: `max_tokens` = cut off mid-JSON, `refusal` = declined. Valid schema ≠ correct values.

## Extended thinking
- Reasoning comes back as a `thinking` block before the answer. On the newest models its content is hidden by default; use `display` for a summary.
- **Adaptive thinking**: model decides depth; tune with **`effort`**. **`budget_tokens` is deprecated → 400** on the newest models.
- **Cost:** thinking tokens are billed **at the output rate**. Deeper thinking costs more even when the answer is the same length.

| Task | Thinking |
|---|---|
| Multi-step reasoning, many constraints, dependent plans | On; match effort to depth |
| Classification, extraction, format conversion, lookups | **Off** |
| Agent planning across tool calls | On for the **planning step**, not every call |

- **Carry-back rule:** with tools, return every `thinking` and `redacted_thinking` block **unchanged** next turn. A signature checks it; editing, summarizing or dropping one gets the request rejected.
- Short on context? Use context engineering, never strip thinking blocks.

## Tool use & schemas
**Claude never runs tools. The full loop:**
1. **Define tools**: `name`, `description`, `input_schema`.
2. **Send the message** with `tools`.
3. **Claude replies with `tool_use` block(s)**: name, unique `id`, input. `stop_reason: tool_use`.
4. **Your code runs each tool.**
5. **Send results**: one `tool_result` per `tool_use`, with matching `tool_use_id`, in the **user** role, in the **very next** user turn. On failure add `is_error: true`.
6. **Claude continues.** Repeat until `stop_reason: end_turn`.

**Rules that fail validation (prompting can't fix them):**
- Missing, mismatched or late `tool_result` → error (e.g. "references unknown tool_use_id").
- N `tool_use` blocks in one turn → all N results in **one** user turn.
- Keep the assistant's whole content array: `text`, `tool_use` and `thinking` blocks.

**Schema design:**
- **Name** it specifically: `get_account_balance`, not `get_data`.
- **Description decides selection**: 3–4 sentences covering what it does, when to use it, **when not to use it**, what it returns.
- `required` only for fields the call can't work without; requiring everything makes Claude **invent values**. Optional fields get defaults.
- Overlapping parameters are the top cause of wrong-tool picks → put boundary language in **both** descriptions; still ambiguous → merge into one tool with a type parameter.
- Independent calls run **in parallel by default**; dependent calls go in separate turns; `disable_parallel_tool_use` forces one per turn.
- Wrong picks that start **after N turns** → suspect the context window before the schema.

### MCP tools
- MCP moves tool definitions and execution into a server. The client sends `ListToolsRequest` and passes the tools to Claude. **Same loop, same pairing rules.**
- MCP tool definitions **cost context even when unused**; connect only what you need.
- API MCP connector: `mcp_toolset` in `tools`, with `default_config` + per-tool `configs` (`enabled`, `defer_loading`). Beta header `mcp-client-2025-11-20`. **Remote HTTP servers only.**

| Transport | Where |
|---|---|
| `stdio` | Local subprocess (stdin/stdout) |
| Streamable HTTP | Remote; SSE-only is **deprecated** |

- MCP when a maintained server covers it; manual schemas when none does or you need control of descriptions; both = MCP for breadth + allowlist + tuned descriptions.

## Streaming
You assemble the message yourself from events:

| Event | Do |
|---|---|
| `message_start` | Start an empty content array |
| `content_block_start` | Open a block at its index; `tool_use` has name + id, **no input yet** |
| `content_block_delta` | Append text, thinking or partial tool JSON |
| `content_block_stop` | Block done; **first moment tool JSON can be parsed** |
| `message_delta` | Read `stop_reason` and usage |
| `message_stop` | Message complete; **now append to history** |

- Never run a tool from partial JSON; never commit a partial turn.
- Stream interrupted → **discard the partial turn and retry** from the last complete one. "Read loop ended" ≠ message complete; the error shows up on the *next* request.
- Skip streaming for short replies or backend jobs nobody watches.

| `stop_reason` | Means |
|---|---|
| `end_turn` | Finished |
| `tool_use` | Run the tools, send results |
| `max_tokens` | Hit `max_tokens`; truncated, may not parse |
| `refusal` | Declined for safety |
| `model_context_window_exceeded` | Hit the context ceiling; trim or summarize |

## Context engineering
- Every tool result stays in context for the session. Production tool outputs are **3–5× bigger** than test fixtures; the window fills at turn 8, not 50.
- Too big → validation error; ceiling mid-generation → `model_context_window_exceeded`. **Never silently truncated.**

| Strategy | What | When |
|---|---|---|
| **Pruning** | Rewind; drop later turns | Dead-end path, debug clutter |
| **Compaction** | Summarize history (`/compact`, API server-side beta, or manual) | Near the ceiling, same task |
| **Clearing** | Empty context (`/clear`, new session) | Totally different next task |
| **Subagent handoff** | Isolated context, returns a summary | Self-contained subtasks |

- Manual compaction: tell the summarizer what to keep (files changed, decisions, errors and fixes).
- **Prompt caching**: `cache_control` type `ephemeral` on the last stable block (≤4 breakpoints). Biggest cost cut for multi-turn: long system prompt, tool definitions, reference docs.
- **`count_tokens`**: same body as a messages call, no inference; gate oversized requests.
- A bigger window isn't the fix for long tasks; **decompose** into subagents.
- **RAG breaks in three places:** chunking (use section-sized chunks with small overlap), embedding match (add lexical search for exact IDs), assembly (wrong structure → model answers from memory).
- Fetch-once index suits a stable corpus and simple lookups; search across rounds suits a changing corpus and multi-step questions.
- Model tiers start at **Sonnet**; change only on eval evidence. Current API models have ≥200k windows; newest flagships 1M.

## Agent construction
- **Agent** = multi-step tool loop + managed context + goal. First ask: **does this need an agent?** Single call → workflow → agent, only as variability demands.

| Workflow when | Agent when |
|---|---|
| Steps can be listed in code | Goal and tools known, path isn't |
| Errors are costly, need step guardrails | Inputs vary unpredictably |
| Same sequence every run | Needs creative tool sequencing |

| Wiring path | Runs the loop | Note |
|---|---|---|
| **Raw Messages API** | Your code | You own everything: loop, retries, context, exit |
| **Agent SDK** | SDK in your process | You still execute tools |
| **Managed Agents** (beta) | Anthropic (loop + sandbox) | Versioned API resource; **sessions stored server-side → not ZDR or HIPAA BAA eligible** |

- Pick the path by **compliance and deployment constraints**, not prototyping speed. PHI/ZDR → SDK or raw loop.

**Four loop steps:**
1. Register tools (start minimal; **over-tooling** is the common failure).
2. Scope the system prompt to the task and tools.
3. Execute every tool call; resolve all calls from one turn together.
4. **Explicit exit condition** that doesn't rely on Claude choosing to stop.

- **Human-in-the-loop**: before destructive/irreversible calls, after planning, on unexpected output. Ask: *worst outcome if this runs unchecked?*
- Exit conditions must cover downstream impact: separate "change proposed" from "write committed".

**Regulated data picks the endpoint first:**

| Constraint | Path |
|---|---|
| HIPAA | BAA-covered config or Bedrock/Vertex; BAA excludes Console, Workbench, betas, consumer plans |
| GDPR / EU residency | Bedrock/Vertex region-pinned; direct API has no EU residency |
| FedRAMP | Claude for Government, Bedrock GovCloud, Vertex Assured Workloads |
| Privilege / internal policy | Direct API from the firm's app with logging; or the endpoint already cleared |

- **Debug checklist (4 layers):** schema (vague description), streaming (commit before `message_stop`), context (dropped thinking blocks, split tool results), memory (concatenating every past session).

## Agent memory
| Scope | Persists | Use when |
|---|---|---|
| In-context | One session; grows every turn | Short sessions |
| **External storage** | DB; inject only what's relevant | Across sessions, users, agent instances |
| Summarized | Condensed history into the next session | Long-running chat agents |
| Stateless | Nothing | Self-contained jobs |

- Decide at **design time** (~20 min) rather than refactoring under pressure (~1 hour). Measure history + system prompt + tool schemas against the limit first.

| Pattern | Loads | Best for |
|---|---|---|
| **Skill** (`SKILL.md`) | Name + description at start; body **on description match** | Task-specific checklists, procedures |
| **`CLAUDE.md`** | Every session | Always-on project standards |
| In-context | Every turn | One-off, short sessions |

- Agent SDK: `CLAUDE.md` loading is controlled by `settingSources`; set it explicitly.
- Skills on the Messages API (beta): headers `code-execution-2025-08-25` + `skills-2025-10-02`; run in the code execution container.
- Subagents **don't inherit Skills or history** (list them); they **do inherit permissions**. Skills are not conversation memory.

## Multimodal & batch
- Images and PDFs use context before any prompt text.
- **Image tokens = ⌈w/28⌉ × ⌈h/28⌉** using post-downscale size. 1000×1000 → 36×36 = **1,296**; 1400×700 → 50×25 = **1,250**.
- Run it on the **largest** production image; a resize step is often the cheap fix.

| Source | Fits |
|---|---|
| Inline base64 | One-off image; sent every request |
| **Files API** (`file_id`) | Reused assets; upload once |
| URL | Also supported |

- **PDF = `document` block**, not `image`. No name field required; optional `title` and `context`.
- Visual prompts should say how to handle overlap, depth and occlusion.
- **Message Batches API**: ≤ **100,000 requests or 256 MB**, returns `batch_id`, **poll**, cheaper, up to **24h**. Results **unordered** → match by **`custom_id`**. Offline only. A loop of sync calls is not batching.
- Good combo: nightly image classification = Files API + Batches + structured outputs.
